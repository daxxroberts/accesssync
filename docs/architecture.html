AccessSync · System Architecture

Seven Layers. One Standard. Infinite Adapters.

AccessSync is not a Wix-to-Kisi connector. It's a platform-agnostic access provisioning engine. Wix and Kisi are just the first adapters. Every new integration multiplies every existing one.

The Seven-Layer Model
Input Zone — Membership Platforms
Layer
1
Membership Connector
adapters/wix/wix-connector.js
HTTP entry point only. Verifies the incoming request is authentic (HMAC-SHA256 signature), then hands the raw payload to Layer 2. Owns no business logic. One connector per membership platform.
Layer
2
Membership Adapter
adapters/wix/wix-adapter.js
Parses the raw platform payload and converts it into a standard event object — the universal language every layer below understands. Zero dependencies. The entire platform translation happens here and nowhere else.
↓
Core Engine — Platform Invariant
Layer
3
Standard Adapter
adapters/standard-adapter.js
Owns all database state. Exclusively controls member_identity, member_access_state, and the in-flight lock that prevents concurrent operations on the same member. No other layer writes these tables.
Layer
4
Core Engine
core/ — webhook-processor · queue-worker · grant-revoke · retry-engine · reconciliation
The orchestration brain. Deduplicates events, queues jobs via BullMQ, coordinates grant and revoke operations, retries on failure, and runs a nightly reconciliation sweep. Knows nothing about Wix. Knows nothing about Kisi.
Layer
5
Hardware Standard Adapter
adapters/hardware-adapter.js
The platform router. Receives a hardwarePlatform string and a standard method call, and delegates to the correct Layer 6 adapter. The Core Engine calls one interface. Hardware adapters implement it however they need to.
↓
Output Zone — Hardware Platforms
Layer
6
Hardware Adapter
adapters/kisi/kisi-adapter.js · adapters/seam/seam-adapter.js
Business logic for a specific hardware platform. Knows concepts like "users", "groups", and "role assignments" in the language that platform uses. Translates standard method calls into the right operations for that system.
Layer
7
Hardware Connector
adapters/kisi/kisi-connector.js · adapters/seam/seam-connector.js
All HTTP calls, authentication headers, rate limiting, and retry logic for one specific platform API. Layer 6 never makes an HTTP call directly — it always delegates to Layer 7. Swapping an API version means touching only this file.
The Standard Event Contract
DR-021 · Platform-Agnostic Event Object
Every platform speaks the same language at Layer 3.
When Layer 2 finishes parsing a Wix webhook — or a Mindbody webhook, or a booking system webhook — it produces exactly this object. Layer 3 and below never know which platform sent the event. They operate entirely on this standard shape.
eventType
string · required
Normalized action — plan.purchased, plan.cancelled, booking.confirmed, member.deleted. Core Engine routes on this, nothing else.
platformMemberId
string · required
The member's unique ID in the source platform. Used for deduplication and DB lookup. Never used directly in the hardware layer.
sourcePlatform
string · required
Which membership platform sent this event — wix, mindbody, etc. Combined with platformMemberId as a UNIQUE key in the DB.
memberEmail
string · required
The member's email address. Used to look up or create the member's account in the hardware platform. The only cross-platform identifier that hardware systems understand.
planId
string · required for grants
The membership plan or product ID from the source platform. The Plan Mapping Resolver uses this to find which hardware groups to assign.
tenantId
string · required
The AccessSync client this event belongs to. Resolved by the Tenant Resolver from the platform's site/account identifier. Every query scopes by this.
Hardware Adapter Interface — Every Hardware Adapter Implements This
Layer 5 Contract — adapters/hardware-adapter.js
The Core Engine calls these eight methods. It does not care what happens inside them. Kisi does it one way. Seam does it another. The engine is the same for both.
findUserByEmail
(apiKey, email) → user | null
Look up an existing member in the hardware platform by email. Returns the platform's user object or null if they don't exist yet.
createUser
(apiKey, memberData) → user
Create a new user in the hardware platform. AccessSync manages users as silent credentials — no welcome emails sent from the hardware system.
assignRole
(apiKey, userId, groupId) → assignment
Grant the user access to a door group. In Kisi this is a role assignment. In Seam this is a different construct. The contract is the same.
removeRole
(apiKey, assignmentId) → void
Revoke access by removing the role assignment. Called when a plan is cancelled or a booking expires. Does not delete the user — just removes the access grant.
suspendAccess
(apiKey, userId) → void
Temporarily disable a member's access without removing their account. Used for payment failures and location subscription lapses. Reversible.
enableAccess
(apiKey, userId) → void
Restore access after a suspension. Called when a failed payment recovers. Pairs exactly with suspendAccess — same user, same state, reversed.
deleteUser
(apiKey, userId) → void
Fully remove the member from the hardware platform. Called only on member deletion — not on cancellation. Permanent. Removes all access grants.
getLocks
(apiKey) → lock[]
Fetch current door lock states. Used by the nightly reconciliation to detect lockdown conditions and skip provisioning on physically locked doors.

Why the Architecture Compounds
1×N
Input × Hardware
Today: 1 membership platform × 1 hardware platform = 1 combination. Every new adapter on either side multiplies the matrix.
Wix × Kisi = 1 integration
4×5
Planned Adapters
4 input platforms × 5 hardware platforms = 20 unique combinations. Each new adapter adds a column or row — all intersections unlock for free.
4 inputs × 5 outputs = 20 combos
0
Core Changes Required
Adding a new adapter changes Layers 1–2 or 6–7 only. Layers 3, 4, and 5 — deduplication, queuing, retries, reconciliation — never change.
Core cost = constant
Four Design Principles That Make This Work
1
Translate at the boundary, not in the core.
Platform-specific knowledge lives only in Layers 1–2 (input) and 6–7 (output). The moment a Wix event enters Layer 3, it's a standard event. The moment the core calls Layer 5, it's a standard method. Neither side knows what the other looks like.
2
One layer owns each concern. No shared ownership.
Layer 3 exclusively owns the database state. Layer 4 exclusively owns job orchestration. Layer 7 exclusively owns HTTP calls. No layer reaches across this boundary. If it does, the architecture has a gap — not a feature.
3
The hardware contract is the product moat.
The 8-method hardware interface — findUserByEmail, createUser, assignRole, removeRole, suspendAccess, enableAccess, deleteUser, getLocks — is the specification every new hardware adapter must satisfy. It encodes years of edge-case knowledge: lockdowns, suspensions, idempotent retries, silent credentials. A competitor building a one-off integration gets none of this.
4
Reliability is built in, not bolted on.
The Core Engine ships with deduplication, an async job queue, an in-flight lock for concurrent safety, exponential backoff retries, a dead-letter queue, nightly reconciliation, and operator email alerts. Every new adapter inherits all of this on day one — for free.
